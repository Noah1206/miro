# 답변 속도 메인 자료 — 스트리밍과 단계별 지연 (2026-10-17)

> 사용자가 속도 개선의 **메인 자료**로 지정한 글이다(2026-10-17). 속도 작업은 이 순서(측정 → 스트리밍 → 순차 호출 줄이기 → 모델·캐싱·프롬프트)를 따른다.
> 원문 아래에 미로의 현재 상태를 대조해 둔다. 설계는 [speed-restructure-2026-10-17.md](../speed-restructure-2026-10-17.md).

## 원문 요지

메시지를 보내고 한참 기다렸다가 답변 전체가 한 번에 나타난다면, 가장 먼저 의심할 것은 스트리밍이 적용되지 않았거나 중간에서 막히는 문제다. AI 생성 자체가 느릴 수도 있지만, 모델을 교체하기 전에 응답을 사용자에게 전달하는 방식부터 확인한다.

- **전체 응답 대기**: AI 가 답을 다 만든 뒤 한꺼번에 표시한다.
- **스트리밍**: AI 가 생성하는 도중 화면에 표시한다.
- 차이는 답을 만드는 능력이 아니라 **생성된 텍스트를 언제 브라우저에 전달하느냐**다. 완성에 6초가 걸려도 첫 글자가 0.8초에 나오면 사용자는 훨씬 일찍 읽기 시작한다.
- 스트리밍은 전체 생성 시간을 줄이는 기술이 아니라 **사용자가 느끼는 대기 시간**을 줄이는 기술이다.

### 1. Gemini 호출 방식

| API | 동작 |
| --- | --- |
| `generateContent` | 답변을 전부 생성한 후 반환 |
| `streamGenerateContent` | 생성되는 답변을 여러 조각으로 반환 |

`streamGenerateContent` 로 바꾸는 것만으로는 충분하지 않다.

### 2. 서버도 스트리밍해야 한다

1. 사용자 메시지 전송
2. 서버에서 필요한 기억과 상황 조회
3. Gemini 스트리밍 API 호출
4. 서버가 생성된 텍스트 조각을 즉시 전달(SSE 등)
5. 브라우저가 텍스트를 점진적으로 출력
6. 생성 완료 후 최종 검증 및 DB 저장

`Gemini → 서버 → 브라우저` 세 구간이 모두 스트리밍되어야 한다. 중간 한 구간이라도 전체를 모아 전달하면 효과가 사라진다.

### 3. 보조 AI 의 순차 호출 줄이기

입력 검열·의미 분석·기억 추출·관계 변화 계산 중 **메인 답변 생성에 반드시 필요한 정보만 먼저** 계산한다. 다음 대화에만 필요한 기억 정리처럼 현재 답변을 바꾸지 않는 작업은 응답 이후로 옮긴다. 단, 안전 검증 전의 내용을 그대로 스트리밍하면 안 된다 — 필요하면 문장 단위 버퍼링이나 스트리밍 가능한 검증을 쓴다.

### 4. 먼저 할 진단 실험

기존 프롬프트 그대로, 보조 AI 와 DB 처리를 빼고 Gemini 만 직접 호출해 세 가지를 잰다.

- **첫 토큰 시간(TTFT)**: 요청 시작부터 첫 응답 조각까지
- **생성 완료 시간**: 마지막 조각까지
- **화면 표시 시간**: 브라우저에 실제 첫 글자가 나타날 때까지

| 측정 결과 | 의심 원인 |
| --- | --- |
| Gemini 도 첫 토큰이 늦음 | 모델·프롬프트·API 대기 |
| Gemini 는 빠른데 서버 전달이 늦음 | 서버 스트리밍·버퍼링 |
| 서버는 빠른데 화면 표시가 늦음 | 프론트엔드 렌더링 |
| 직접 호출은 빠른데 전체는 느림 | 보조 AI·DB·검열 등 추가 처리 |

### 5. 개선 순서

1. 모델·프롬프트 유지, 단계별 지연 측정과 스트리밍부터.
2. 의미 분석·기억 추출·DB 조회의 실행 순서를 보고 병렬화할 작업을 분리.
3. 그다음에야 모델 변경·캐싱·프롬프트 길이 축소.

목표는 전체 응답을 빨리 끝내는 것이 아니라, **캐릭터가 최대한 빨리 반응하기 시작하면서도 관계·기억 기능을 유지하는 것**이다.

| 서버 → 브라우저 | 대사 블록이 완성되는 대로 보냄(`blockStream`, 54fdcc4). 대화 방식 검토가 필요한 턴만 모아서 보냄 | 됨(검토 턴 제외) |
| 브라우저 표시 | 타자 효과(dd4dfb6) | 됨 |
| 순차 호출 | **계획(agency_plan) → 대사(dialogue)** 가 직렬. 첫 글자 전 계획이 끝나야 한다 | **병목** |
| 진단 실험 | 아래 표 | 10/17 측정 |

### 진단 실험 결과 (10/17, 실제 요청을 Gemini 에 직접, 위로 장면)

| 호출 | 첫 조각(TTFT) | 끝 | 출력 토큰 | 생각 토큰 |
| --- | --- | --- | --- | --- |
| 계획 gemini-3.8-flash | 2.3~4.8초 | 8.7~9.7초 | 805~1188 | 0 |
| 대사 gemini-3.8-flash | 2.3~3.5초 | 5.0~6.1초 | 340~456 | 0 |
| 한 문장 요청 gemini-3.8-flash | 1.8~2.8초 | — | — | — |
| 한 문장 요청 gemini-3.5-flash-lite | 0.65~0.70초 | — | — | — |

- 생각 토큰은 0 이다(thinkingLevel low). 3.8 Flash 는 `minimal` 을 받지 않는다(400).
- **3.8 Flash 는 프롬프트가 짧아도 첫 조각까지 약 2~3초가 고정으로 든다.** 프롬프트 길이(약 9천 토큰)는 큰 원인이 아니다.
- 기준표 13장면 중앙값: 첫 블록 12.2초 = 준비 ~0.5초 + **계획 7.7초**(TTFT ~3초 + 출력 ~840 토큰) + 대사 첫 블록 ~4초(TTFT ~3초 + 첫 블록).
- 결론(원문 표 기준): "직접 호출은 빠른데 전체는 느림" — 서버·화면 전달이 아니라 **계획 호출이 대사 앞에 직렬로 놓인 것**이 첫 글자를 늦춘다. 원문 개선 순서 2단계(순차 호출 분리)에 해당한다.
