목표
이미 배포한 허구 회상·반복 표현·문자 무응답 수정이 실제 경로에서도 동작하는지 확인한다. 코드를 읽고 테스트 통과만 보고 끝내지 말고, 실제 모델 출력과 저장 결과를 근거로 판단한다. 100턴 이상 장기 실험은 재개하지 않는다.
Opus는 이 작업을 수행하는 코딩 에이전트다. 앱의 Gemini·Sonnet 역할을 Opus로 교체하라는 뜻이 아니다. 사용 중인 에이전트 모델은 실행 환경에서 확인하며, 확인할 수 없으면 단정하지 않는다.

1. 현재 상태부터 확인
- AGENTS.md 등 적용 지침과 관련 스킬을 읽고 git status, git log를 확인한다. 다른 미커밋 작업을 보존한다.
- docs/verification/2026-10-16-conversation-fixes.md와 conversation-fixes-next-steps.md를 읽는다.
- 당시 앱 배포 커밋은 423297f, 후속 점검 스크립트 커밋은 77de239였다. 현재 버전은 새로 확인하며 이 값으로 되돌리지 않는다.
- 운영 환경의 MIRO_FEATURE_STRICT_CONVERSATION_REVIEW와 MIRO_AGENCY_VERIFY_MODEL_ID 적용 여부를 비밀값 없이 확인한다. 배포 설정만 보고 실제 호출 성공으로 판단하지 않는다.
- 중단된 자동화 24, 3-125와 기존 데모·장기 실험을 재개하지 않는다. 기존 결과와 실패 기록을 수정하지 않는다.

2. 기존 검사를 실행하고 결과를 저장
bash scripts/verify-conversation-fixes.sh --health
bash scripts/verify-conversation-fixes.sh --unit
bash scripts/verify-conversation-fixes.sh --db-tests
bash scripts/verify-conversation-fixes.sh --audit-messenger

- DB 테스트는 전용 로컬 miro_reality_test에서만 실행한다. 운영 DB에 fixture를 넣지 않는다.
- 운영 감사는 집계 읽기만 한다. 개별 실제 사용자 대화·인증키·토큰을 출력하지 않는다.
- 필요한 환경·도구가 없으면 해당 검사를 미실행으로 기록한다. 실패를 통과로 간주하지 않는다.

3. 짧은 실제 대화 확인
- 기존 안전한 테스트 도구와 실제 앱 API 경로를 먼저 읽는다. 별도의 신규 전용 테스트 계정·방을 사용한다. 중단된 박도하 데모나 실제 사용자 계정에는 보내지 않는다.
- 공개된 성인 일반 모드 캐릭터 중 성격이 다른 3명을 선택한다. 성적 대화는 필요 없다.
- 각 캐릭터에 최대 4번, 총 12번의 사용자 발화만 제출한다. 모델 재시도·검토를 포함하여 최대 60회 호출 및 추정 공급자 비용 US$3 중 먼저 도달하는 한도에서 중단한다. 비용을 산정할 수 없거나 기존 승인 예산이 더 작으면 추가 유료 호출을 멈추고 한계를 보고한다. 충전·예산 상향은 하지 않는다.
- 실제 모델 호출 직전부터 비용과 호출 수를 기록한다. 응답이 pending이면 중복 제출하지 않는다. 실패 시 API의 재시도 계약과 요청 ID를 따른다.
- 캐릭터별로 다음 흐름을 자연스럽게 진행하되 응답을 읽고 다음 입력을 조정한다.
  첫째: 처음 만났다는 전제와 사용자의 작은 취향·오늘의 고민을 말한다.
  둘째: 그 취향 하나를 정정하고, 같은 위로나 질문을 반복하지 말아 달라고 말한다.
  셋째: '다음에 같이 산책하면 좋겠다' 같은 미래 제안을 한다. 과거에 함께 했다고 말하지 않는다.
  넷째: 바로 앞 맥락의 구체적인 질문을 한다. 정정된 취향과 미래 제안을 과거 사실로 바꾸지 않는지, 인물의 고유 말투가 유지되는지 본다.
- 입력·실제 출력·요청 ID·시각·사용 모델·저장 여부·관계 전후 값을 테스트 계정에 한정해 기록한다. 관계 수치와 기억은 직접 수정하지 않는다. 4턴으로 장기 기억이나 관계 체감이 검증됐다고 쓰지 않는다.
- 테스트 계정 생성이나 실제 경로 사용이 불가능하면 모의 결과로 대체하여 실사용 성공이라고 보고하지 않는다. 가능한 읽기 검사와 로컬 검사는 계속한다.

4. Gemini와 검증 모델의 실제 역할 확인
- 위 호출의 실제 trace에서 agency_plan, dialogue, memory_extraction, agency_verify 등의 모델과 성공 여부를 확인한다. 모든 단계가 매 턴 호출될 것이라고 가정하지 않는다.
- Gemini의 성공 응답과 대체 모델의 성공을 구분한다. Gemini 503 후 Sonnet이 답했다면 'Gemini 정상'으로 기록하지 않는다.
- 모델·공급자·온도·재시도 한도·예산을 바꿔 통과시키지 않는다. 장애 시 무한 재전송하지 않는다.
- 소스 검토가 실제로 실행됐는지와 허구 회상을 막았는지를 구분해 기록한다. 일반 공감·조건문·제안의 오차단도 실패로 취급한다.

5. 문자 무응답 확인
- 읽은 질문의 wait/defer/공급자 실패가 read 상태와 다음 검토 시각을 보존하는지, 새 unread보다 우선 처리되는지, 답장이 한 번만 생성되는지 로컬 DB 회귀 검사와 코드 경로로 확인한다.
- 운영 실수신은 신규 전용 테스트 방에서 실제 문자 기능을 사용할 수 있고 위 한도에 여유가 있을 때만 시험한다. 이 문자 발화도 총 12회에 포함한다.
- 질문 제출 후 자연 cron으로 읽음→보류 또는 답장→문자 목록 저장까지 관찰한다. 강제 cron·직접 발송·과거 left 되살리기·비활동 시각/연락 확률/관계/quiet hours 변경은 하지 않는다.
- 최대 30분 범위에서 관찰하되 도구의 한 번 대기는 60초 이하로 한다. 기존 관찰 수단이 있으면 사용한다. 새 예약 자동화는 만들지 않는다. 시간 안에 답장이 없으면 '미확인' 또는 증거가 있는 '실패'로 남긴다. 답장을 만들기 위해 사용자 발화를 추가하지 않는다.
- 실제 연락 생성, 푸시 서버 수락, OS 기기 수신은 별도 결과다. 기기 수신을 보지 못하면 미확인으로 기록한다. 기존 사용자 기기 구독을 건드리지 않는다.

6. 결함이 재현되면 공통 코드에서 수정
- 단일 캐릭터용 예외로 숨기지 않는다. 원인과 재현 근거를 먼저 적고 최소 수정한다.
- 핵심 파일: packages/engine/src/agency/conversation-review.ts,
  packages/engine/src/conversation-repetition.ts, packages/engine/src/agency-turn.ts,
  packages/engine/src/orchestrator.ts, apps/web/lib/messenger/reply-disposition.ts,
  apps/web/lib/messenger/inbox.ts, apps/web/lib/reality/agency.ts.
- 허구 사실 주장과 가정·권유를 구분한다. 다른 인물의 대사와 짧은 인사는 반복으로 오차단하지 않는다. '반복하지 마'를 반복 허용으로 해석하지 않는다.
- 최소 재현 회귀 테스트와 필요한 타입 검사를 실행한다. 실패한 실제 출력은 보존한다. 예산 안에서만 짧게 재확인한다.
- 수정이 있다면 miro-ship 스킬에 따라 필요한 파일만 커밋하고 운영 배포·health·원격 푸시까지 완료한다. DB 변경이 필요하면 관련 Supabase 지침을 먼저 읽는다. 수정이 없다면 불필요하게 배포하지 않는다.
