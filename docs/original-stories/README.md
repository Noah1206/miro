## 2. 데이터 구조 (마이그레이션 `20261015120000_original_stories.sql`, `20261015120100_story_contacts_cron.sql`)

| 표 | 역할 |
|---|---|
| `stories` | 공개 정보만(`public` jsonb = 제목·소개·장르·태그·역할·안내·첫 장면·인물 공개 프로필). `is_published` 기본 false. `seeded_hash` 로 운영자 수정 감지 |
| `story_private` | 서버만 읽는 정의(세계 운영 지시·제작자 진실·사실 목록·인물 지시문·사건 조건·효과·결말 조건·연락 규칙). 공개 조회 코드는 이 표를 읽지 않는다 |
| `story_runs` | 사용자 × 작품 × 회차. `state`(현재 사건·완료·선택·변수·인물별 신뢰/호감/연락/경계/관계 결말·누가 무엇을 아는지·기억·약속·장면 수), `version`(낙관적 잠금), 살아 있는 회차는 (사용자, 작품)당 하나(새 회차를 시작하면 이전 것은 `archived`, 삭제 안 함) |
| `story_turns` | 입력 하나 = 턴. `(run, client_turn_id)` 고유 → 재시도·새로고침은 저장된 결과를 그대로 돌려줌. 회차당 진행 중 턴 하나(부분 고유 색인) → 동시 요청은 `busy` |
| `story_messages` | 장면(서술+대사 블록)과 인물별 연락석 스레드. 읽음 시각 |
| `story_changes` | 모든 상태 변경과 거부를 원인 턴·메시지와 함께 기록 |
| `story_contacts` | 연락석 예약. `(run, key)` 고유 = 같은 연락은 회차에 한 번. pending/sent/cancelled + 사유 |

원고의 상태 키는 제안이었으므로 그대로 DB 컬럼으로 만들지 않고 작품 정의의 `vars`(int/bool/set/enum)와 공통 관계 상태로 옮겼다.

## 4. 턴 한 번의 흐름

1. 턴 확보: 회차 잠금 → 같은 `client_turn_id` 면 캐시 반환 / 다른 입력이면 conflict / 진행 중 턴이 있으면 busy.
2. 해석 모델(`world_update` 작업)이 행동을 **제안**: 선택(option/pick), 신뢰·호감, 연락 허용/중지, 경계, 독점, 관계 결말, 기억·약속, 전제 거부/수락, 시간 이동, 확인 질문. 모든 행동은 `quote`(유저 입력의 실제 문장)가 있어야 한다.
3. 엔진이 검증·적용: 근거가 입력에 없으면 거부(유저가 하지 않은 고백·접촉 확정 방지), 현재 사건의 선택인지, 조건(증거 수 등) 충족인지, 신뢰는 사건당 인물별 +1·상한, 호감은 명시적 연애 표현만, 연인은 신뢰·호감·연락·독점 게이트, 결말 사건은 진로 + 모든 인물 관계가 정해져야 끝. 값은 모델이 아니라 정의의 효과에서 나온다.
4. 서술 모델(`dialogue`)이 장면 생성: 지금 사건 상황만, 인물마다 **그 인물이 아는 사실만**, 유저가 아는 단서, 기억·약속(연락석에서 맺은 약속 포함), 반영된/거부된 행동, 확인 질문. 제작자 진실·미래 사건·엔딩 조건·연락 규칙은 보내지 않는다. 비밀을 암시하는 말투 예시는 `lineGates` 조건이 맞을 때만.
5. 한 트랜잭션 저장: 버전 확인 → 메시지·원장·상태(+1 버전)·연락 예약 정리 → 턴 완료.

연락석(DM) 턴도 같은 길이며, 선택·결말·시간 이동은 장면에서만 된다.

## 5. 연락석(선톡)

- 예약: 상태 저장 때 규칙의 `when` 이 처음 참이 되면 `story_contacts` 에 한 줄(중복 키 불가). 상태가 바뀌어 `cancelIf` 가 참·`when` 이 거짓·연락 중지·전제 거부면 즉시 취소.
- 발송(크론 5분, `work=story`): 회차를 잠그고 게이트를 다시 본다 — 중복 키 → 연락 중지 → 전역 허용(`push_enabled`)·작품 수신 동의·인물 허용 → 시간대(모르면 보류, 화면에서 설정) → 작품 기본 휴식 22~09시 + 사용자 휴식 시간 → 진행 중 장면(최근 10분 입력) → 취소 조건 → 다음 장면 대기 → 작품 하루 2건 → 인물별 미읽음 1건 → 인물별 8시간 간격. 보류는 15분 뒤 다시, 취소는 사유 기록.
- 문안은 원고의 고정 문장만 보낸다(모델 생성 아님) → 하지 않은 약속을 지어낼 수 없다.
- 기존 전역 선톡 정책(하루 1~5통·90분 간격 등)은 바꾸지 않았다. 원고 제안값(하루 2·8시간·미읽음 1·22~09시)은 작품별 `contactPolicy` 로만 적용.
- 외부 푸시는 `storyPush` 플래그가 켜졌을 때만, 잠금화면엔 인물 이름 + "새 연락이 도착했어요."만. 현재 꺼짐.
- 이야기 시간은 장면 진행·합의된 시간 이동으로만 흐른다. 현실 미접속으로는 아무 상태도 바뀌지 않는다.

## 8. 미검증·남은 문제

1. **실제 모델(Claude) 호출 0회.** 자유 입력 해석 정확도, 모호할 때 확인 질문, 인물이 모르는 것을 말하지 않는지, 장면 품질·속도는 확인 못 했다. 예상 비용: 턴당 약 $0.02~0.04(해석 + 장면), 5작품 × 8턴 실측이면 약 $1~2.
2. **실제 푸시·기기 도착·읽음** 미검증(플래그 꺼짐, 운영 크론 미등록).
3. 이용권/미로 단위 차감 없음 — 스토리 턴은 지금 사용량을 깎지 않는다(운영자 AI 예산 한도만 적용). 공개 전 결정 필요.
4. 화면 문구 번역(en/ja/zh) 없음 — 한국어로 보인다.
5. 스토리 연락석은 전역 채팅 목록·알림 종 숫자에 아직 안 잡힌다(스토리 화면 탭의 점으로만).
6. 약속 후속 연락을 다른 연락보다 먼저 보내는 우선순위 — 규칙 연락만 있고 '약속 후속' 연락은 아직 없다.
7. 작품 정의를 바꾸면 진행 중 회차도 새 정의를 읽는다. 변수·사건을 지우는 큰 변경이면 `version` 을 올리고 회차 이전 방법을 정해야 한다.
8. 작품 변환 중 엔진으로 표현하지 못해 단순화한 것(작품별 상세는 각 파일 머리 주석): 인물 쪽 동의를 별도로 기록하지 못해 선택지로 나눔(3번), 시간 이동이 변수를 못 바꿔 '하루 넘기기' 선택으로(2번), 연락 문안을 상태별로 바꾸지 못해 규칙을 나눔(5번), 경계 삭제·수정 없음(5번 QA7 은 추가 방식).

10. 개발 서버가 `apps/web/tsconfig.json` 을 자동 수정했다(되돌림). 미리보기 설정 `web-testdb-mock` 을 `.claude/launch.json` 에 추가했다.

## 9. 운영 공개 전에 필요한 조치

1. 운영 DB 에 마이그레이션 2개 적용(두 번째는 운영 pg_cron 에 5분 작업을 등록한다).
2. 운영 시드: `seed-stories.mts --apply --allow-remote` (작품은 비공개로 들어간다).
3. 실모델 실측(금액 상한 승인 후) — 해석·비밀 유지·확인 질문·장면 품질.
4. 이용권 차감 방식 결정, 번역, 채팅 목록 연동 여부 결정.
5. 표지·인물 이미지 제작(사용자 동의 후) 및 `stories.public` 이미지 필드 추가.
6. 공개: 작품별 `is_published = true` (운영자 확인). 그 전까지 운영 홈에는 아무것도 안 보인다.
7. 외부 푸시를 쓰려면 `MIRO_FEATURE_STORY_PUSH=1` + 실기기 확인.

## 10. 전역 문자·푸시 연결 (2026-10-15)

### 구현

- `/archive`와 데스크톱 채팅 목록에 일반 대화와 스토리 인물별 연락을 함께 조회한다. 사용자 소유 회차만 읽으며, 작품명·회차·인물·최근 문자·미읽음 숫자를 제공한다. 두 종류를 합친 뒤 동일한 커서로 정렬·페이지를 나눈다. `/messages`는 이 목록으로 이동한다.
- 스토리 문자 주소는 `/messages/story/{runId}/{characterKey}`. 기존 `ChatTheme`, `MessengerThread`, 문자 CSS를 재사용하고 답장은 스토리 턴으로 저장한다. 일반 캐릭터챗 기억으로 복사하지 않는다. 플레이 화면과 같은 메시지를 읽고, 홈 알림 숫자도 같은 읽음 상태를 센다.
- 새 회차를 시작하면 이전 회차 문자는 보관된다. 보관된 회차는 읽기만 가능하며 알림 숫자·푸시에서 제외된다.
- 읽음 처리는 화면에서 확인한 메시지 ID만 대상으로 한다. 열어 둔 화면은 주기적으로 갱신한다.
- `storyPush` 기본 활성화(환경변수 `MIRO_FEATURE_STORY_PUSH=0`으로 중단 가능). **기존 과거 문자에 대한 푸시 소급 생성은 없다.** 새로 도착하는 선톡만 메시지 저장 트랜잭션 안에서 구독별 `story_push_jobs`에 적재한다.
- 크론 `work=story`가 연락과 푸시를 함께 처리한다. 재시도·워커 임대·최대 5회 시도·만료 구독 해제·기록을 갖춘다. 잠금화면에는 이름과 번역된 새 연락 안내만 보낸다. 인물마다 알림 태그를 구분한다.
- 외부 발송 직전에 사용자 삭제, 보관, 연락 중지, 읽음, 전역 알림 허용, 수신 동의, 휴식 시간, 구독 소유권을 다시 검사한다. 12시간 지난 알림은 취소한다. 한 연락의 오류가 다른 연락 처리를 중단시키지 않는다.
- 최초 수신 동의는 미리 체크하지 않는다. 문자·기기 알림을 받는다는 설명과 휴식 시간을 알린다. 인물별 스위치는 그대로 제공한다.
- 주요 플레이·시작 UI와 푸시 안내에 en/ja/zh를 적용했다. **작품 원고, 소개, 선택 예시, 장면·연락 문안의 완전한 다국어 현지화는 별도 작업이다.**

### 검증과 운영

- 신규 마이그레이션: `20261015130000_story_reality_inbox.sql`(CLI 생성 후 기존 12:00 스토리 마이그레이션 뒤로 정렬). 새 큐는 RLS 활성화, anon/authenticated 직접 접근 차단, 외래키 cascade와 조회 인덱스를 둔다.
- 스토리 및 기존 보관함 회귀 테스트 **162개 통과**, 신규 문자·푸시 통합 테스트 13개 포함. 실패 재시도, 병렬 워커 중복, 소유권 분리, 회차 보관, 미읽음, 늦게 도착한 메시지의 읽음 보호를 검증했다.
- 기존 테스트 DB에 없던 contact_boundary/narrative_calendar 컬럼은 기존 마이그레이션을 적용해 맞췄다. 운영에는 이미 존재하므로 재적용하지 않는다.
- 운영 사전 확인: 5분 크론 활성 및 heartbeat 정상. 공개 작품 4개, `original-beauty`는 비공개 상태를 유지한다.
- 운영 DB에서 실모델 장면 생성 → 검증된 행동 6개 적용/거부 0개 → C2 선톡 예약을 확인했다. 운영자 점검용 회차를 사용했다.
- 푸시 테스트의 대상은 운영자가 지정한 계정으로 제한한다. 테스트 시 예약 대기 시간을 줄였다면 자연 대기와 구분해 보고한다. 공급자 전송 성공은 실제 기기 표시 확인과 구분한다.

### 기획 결정이 남은 부분

1. **요금:** 스토리 턴은 미로를 차감하지 않는다. 하지만 기존 AI 사용자별 일·월 원가 한도와 전체 예산 보호를 받는다. 체험 횟수, 장면/문자별 과금, 한도 도달 안내를 정해야 한다. 권장 출발점은 무료 도입부 후 장면 진행에 과금하고 수신·읽음은 무료로 두는 방식이다. 이번 변경에서 요금을 임의로 추가하지 않는다.
2. **연락 빈도:** 현재 작품마다 하루 2통·인물별 8시간이다. 여러 작품과 일반 리얼리티를 함께 쓰는 사용자의 합산 알림 상한을 정해야 한다.
3. **시즌 종료 이후:** 기존 문구는 일상이 계속된다고 안내한다. 후일담·일상 연락을 지속 제공할지, 시즌 종료로 마칠지 콘텐츠 범위를 확정해야 한다. 약속 후속 연락의 우선순위도 아직 별도 기능이다.
4. **정의 버전:** 운영 중 사건·변수를 바꾸는 큰 개정은 기존 회차 이관 정책과 함께 진행해야 한다.
5. **현지화와 공개:** UI 번역과 작품 번역은 별개다. 한국어 원고의 다국어판과 현재 비공개 작품의 공개 시점은 별도로 결정한다.
