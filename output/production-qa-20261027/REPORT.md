# Miro 실제 운영 배포 검증

- 확인일: 2026-10-27 KST
- 대상: https://miroapp.app
- 방식: 실제 로그인 세션의 브라우저 조작, 공개 health·PWA manifest, Vercel 읽기 전용 배포 조회
- 화면: 데스크톱 1280px와 모바일 크기 430px. 실제 iPhone·Android 기기 검사는 아님
- 증거: 브라우저 관측 18개, 캡처 23개. 일부 캡처는 로딩·중간 화면이므로 아래 지정한 증거를 우선한다
- 운영 코드·환경·DB 스키마 변경, 새 배포, 실제 메시지 전송, 유료 AI 호출, 결제, 본인인증 제출, 동의 저장, 알림 발송은 하지 않음
- 홈 취향 선택과 채팅 안내 완료는 브라우저 선호·안내 상태에 영향을 줄 수 있다. 만들기 진입 시 draft 식별자가 발급된 URL을 확인했지만 값을 입력·저장·게시하지 않았고 이후 임시저장 목록은 0개였다

## 결론

**운영 서비스는 응답하지만, 최근 구현 내용을 모두 반영한 배포가 아니다.**

최신 GitHub 커밋은 `433f5fb3`(학습 문서), 최신 UI 변경은 `07fc57cb`다. 읽기 전용 Vercel 목록에서 최신 Production은 다음과 같았다.

- 생성 시각: **2026-10-25 01:01:44 KST**
- 상태: Ready
- 배포 주소: https://miro-1ezz0ym7u-noah1206s-projects.vercel.app
- 연결 alias: miroapp.app / www.miroapp.app / miro-web-ashen.vercel.app
- 최근 푸시 이후의 새 배포는 조회 목록에 없었다

공개 health는 `HTTP 200`, `ok=true`, `db=up`, `schema=ready`, `cron=fresh`였다. 다만 `version` 값이 빈 문자열이라 이 응답으로 운영 소스의 정확한 커밋을 식별할 수 없다. 최근 변경과 맞지 않는 실제 UI도 직접 확인했다. 특정 GitHub 연동 설정이 원인이라고까지 조사·확정한 것은 아니다.

## 재현 가능한 주요 문제

### 1. 최신 배포와 요구 화면이 일치하지 않음 — P1

- 경로: `/home`
- 동작: 전체 선택 버튼 열기. 최초 접속과 재진입 후 다시 재현
- 기대: 남성향·여성향 없이 BL 탐색 조건 표시,5개 내비게이션
- 실제: 예전 전체/남성향/여성향 선택과4개 내비게이션
- 증거: [모바일 재현](screenshots/14-audience-reproduced-mobile.png), [데스크톱 홈](screenshots/02-home-old-nav.png)
- 관련된 여러 UI 불일치를 독립 원인 수십 개로 과장하지 않는다. 같은 배포 불일치에 속한다

### 2. 새 검색 결과 경로404 — P1

- 경로: `https://miroapp.app/search/results`
- 동작: 직접 접속 후 새로고침으로 재확인
- 기대: 새 검색 결과 페이지
- 실제: 404 / This page could not be found.
- 증거: [404 화면](screenshots/08-search-results-404.png)
- 예전 검색은 작동하므로 모든 검색이 고장났다는 뜻은 아니다

### 3. 보류한 음성 모드가 운영 메뉴에 노출 — P1

- 경로: 기존 채팅방의 대화 메뉴
- 동작: 안내를 마친 후 메뉴 열기
- 기대: 음성 보류 상태에서 음성 모드가 보이지 않음
- 실제: 채팅 모드와 음성 모드가 함께 표시
- 증거: [메뉴](screenshots/12-chat-menu-voice-still-visible.png)
- 모드를 켜거나 유료 합성을 호출하지 않았다. 백엔드 차단 여부를 이 UI만으로 단정하지 않는다

### 4. 인증·설정·입력 디자인 미반영 — P2

- 성인인증: [전체 페이지](screenshots/04-verification-is-full-page.png)
- 언어·페르소나·권한·AI 설정: `05-*.png`와 `06-permissions-recheck.png`
- 제목28px/600, 입력16px/placeholder13px는 브라우저 계산 스타일로 측정
- 필수 동의와 실제 인증 경로 자체의 성공·실패는 제출하지 않아 미검증

## 콘솔·반응형 관측

- 기록한18개 브라우저 관측의 error/warn 로그는0개였다. 모든 경로의 전체 로그나 네트워크 오류가 없다는 뜻은 아니다
- 새 경로404는 별도 확인했다
- 측정한430px 화면에서 문서 가로 넘침은 관측하지 않았다
- 데스크톱1280px 홈·프로필도 확인했다
- 앱 전체 건강 점수는 산정하지 않는다. 최신 배포와 불일치하고 생성·저장·과금 검증이 빠진 상태에서 숫자 하나로 전체 정상 여부를 표현하면 오해를 낳는다

## 우선순위와 검증 경계

1. 최신 UI 커밋을 포함하는 운영 배포인지 먼저 맞춰야 한다. 이번 검증에서는 배포를 실행하지 않았다
2. 최신 배포를 대상으로5개 내비·탐색·검색·프로필·설정·인증 시트·음성 보류를 다시 확인해야 한다
3. 이후 분리된 테스트 계정·허용된 생성 예산으로 저장·실제 AI 응답·이미지·사용량·실패 환급을 검증해야 한다

현재 결론은 **운영 기반과 일부 기존 기능은 동작하지만, 지금까지의 최신 구현 전체가 운영에서 동작한다고 승인할 수 없다**는 것이다.

## 증거 파일

- `health.json`: 공개 서버 상태
- `deployment-inspect.txt`: 실제 alias와 생성 시각
- `manifest.json`: PWA 정적 설정
- `browser-checks.json`: DOM 기반 측정과 검사 범위
- `screenshots/`: 화면 캡처. 로그인된 계정 화면이 포함되므로 이 검증 폴더는 공개 저장소에 자동 업로드하지 않음

마지막 브라우저 화면 크기 재정의는 복원했고 localhost 작업 탭은 유지했다.
